### Chương 12: Tài liệu hóa API

Chương 12 của cuốn sách *The Design of Web APIs* tập trung vào việc tài liệu hóa API, một yếu tố quan trọng để đảm bảo rằng các nhà phát triển (người tiêu dùng API) có thể dễ dàng hiểu và sử dụng API. Tài liệu hóa không chỉ là việc cung cấp thông tin kỹ thuật mà còn là việc tạo ra trải nghiệm tốt cho người dùng API, giúp họ đạt được mục tiêu một cách dễ dàng. Dưới đây là nội dung chi tiết của chương này, được trình bày bằng tiếng Việt.

---

#### 12.1 Tạo tài liệu tham khảo (Reference Documentation)

**Tổng quan**  
Tài liệu tham khảo là loại tài liệu chính cung cấp mô tả chi tiết về tất cả các thành phần của API, bao gồm dữ liệu, mục tiêu (goals), và bảo mật. Mục đích là giúp các nhà phát triển hiểu cấu trúc và cách thức hoạt động của API một cách chính xác và rõ ràng.

##### 12.1.1 Tài liệu hóa mô hình dữ liệu (Documenting Data Models)

- **Mô tả mô hình dữ liệu**:  
  Tài liệu hóa mô hình dữ liệu liên quan đến việc mô tả các định dạng dữ liệu được gửi hoặc nhận bởi API, thường sử dụng JSON Schema trong OpenAPI Specification (OAS).  
  - Ví dụ: Một thuộc tính như `date` phải được mô tả rõ ràng là định dạng ngày giờ theo chuẩn ISO 8601 (ví dụ: `2025-06-15T11:38:00+07:00`).  
  - Các thuộc tính cần được mô tả chi tiết, bao gồm:  
    - **Loại dữ liệu** (string, number, boolean, v.v.).  
    - **Định dạng** (nếu có, ví dụ: `date-time` cho ngày giờ).  
    - **Bắt buộc hay không** (required hay optional).  
    - **Giá trị ví dụ** để minh họa cách dữ liệu trông như thế nào.  
  - JSON Schema trong OAS cho phép mô tả các đối tượng phức tạp, bao gồm các thuộc tính lồng nhau (nested properties) và các mảng (arrays).  

- **Tầm quan trọng**:  
  - Giúp người tiêu dùng API hiểu chính xác dữ liệu mà API trả về hoặc yêu cầu.  
  - Tránh nhầm lẫn khi sử dụng dữ liệu, ví dụ: nhầm lẫn giữa định dạng chuỗi (string) và số (number).  
  - Đảm bảo rằng các nhà phát triển có thể tích hợp API một cách chính xác mà không cần phải đoán định dạng dữ liệu.

- **Ví dụ trong OAS**:  
  Một mô hình dữ liệu đơn giản trong OAS có thể trông như sau:
  ```yaml
  schemas:
    User:
      type: object
      properties:
        id:
          type: string
          example: "12345"
        name:
          type: string
          example: "Nguyen Van A"
        email:
          type: string
          format: email
          example: "nguyenvana@example.com"
      required:
        - id
        - name
  ```
  Trong ví dụ này, mô hình `User` được định nghĩa với các thuộc tính `id`, `name`, và `email`, trong đó `id` và `name` là bắt buộc.

##### 12.1.2 Tài liệu hóa mục tiêu (Documenting Goals)

- **Mô tả mục tiêu**:  
  Mục tiêu (goals) của API là các hành động mà người tiêu dùng có thể thực hiện, như tạo, đọc, cập nhật, hoặc xóa tài nguyên (CRUD). Trong OAS, các mục tiêu được mô tả thông qua các thao tác (operations) trên các đường dẫn (paths).  
  - Mỗi mục tiêu cần được mô tả với:  
    - **Đường dẫn (path)**: Ví dụ, `/users/{id}`.  
    - **Phương thức HTTP** (GET, POST, PUT, DELETE, v.v.).  
    - **Tham số (parameters)**: Bao gồm tham số đường dẫn (path parameters), tham số truy vấn (query parameters), hoặc dữ liệu trong body.  
    - **Phản hồi (responses)**: Mô tả các mã trạng thái HTTP (200, 404, v.v.) và nội dung phản hồi.  
    - **Mô tả (description)**: Giải thích rõ ràng mục đích của mục tiêu.  

- **Ví dụ trong OAS**:  
  Một mục tiêu để lấy thông tin người dùng có thể được mô tả như sau:
  ```yaml
  paths:
    /users/{id}:
      get:
        summary: Lấy thông tin của một người dùng theo ID
        description: Trả về chi tiết của người dùng dựa trên ID được cung cấp
        parameters:
          - name: id
            in: path
            required: true
            schema:
              type: string
        responses:
          '200':
            description: Thành công, trả về thông tin người dùng
            content:
              application/json:
                schema:
                  $ref: '#/components/schemas/User'
          '404':
            description: Không tìm thấy người dùng
  ```
  Trong ví dụ này, mục tiêu `GET /users/{id}` được mô tả với tham số đường dẫn `id`, phản hồi thành công (200) trả về mô hình `User`, và phản hồi lỗi (404) khi không tìm thấy người dùng.

- **Tầm quan trọng**:  
  - Tài liệu hóa mục tiêu giúp nhà phát triển hiểu cách gọi API và xử lý các phản hồi.  
  - Cung cấp thông tin về các trường hợp lỗi có thể xảy ra (như 404 Not Found) để nhà phát triển chuẩn bị xử lý phù hợp.  
  - Đảm bảo rằng các nhà phát triển không cần phải đoán cách API hoạt động.

##### 12.1.3 Tài liệu hóa bảo mật (Documenting Security)

- **Mô tả bảo mật**:  
  Bảo mật là một phần quan trọng của API, và tài liệu tham khảo phải mô tả rõ ràng cách API được bảo vệ. Trong OAS, bảo mật được mô tả thông qua phần `components/securitySchemes`.  
  - Các khía cạnh cần tài liệu hóa:  
    - **Loại bảo mật**: Ví dụ, OAuth2, API key, hoặc Basic Authentication.  
    - **Quy trình đăng ký**: Làm thế nào để người tiêu dùng API nhận được thông tin xác thực (credentials)?  
    - **Cách sử dụng thông tin xác thực**: Ví dụ, thêm token vào header `Authorization`.  
    - **Phạm vi (scopes)**: Nếu sử dụng OAuth2, mô tả các phạm vi truy cập (scopes) mà API hỗ trợ.  

- **Ví dụ trong OAS**:  
  Một mô tả bảo mật sử dụng OAuth2 có thể trông như sau:
  ```yaml
  components:
    securitySchemes:
      oauth2:
        type: oauth2
        flows:
          authorizationCode:
            authorizationUrl: https://example.com/oauth/authorize
            tokenUrl: https://example.com/oauth/token
            scopes:
              read: Đọc dữ liệu
              write: Ghi dữ liệu
  security:
    - oauth2: [read, write]
  ```
  Trong ví dụ này, API sử dụng OAuth2 với hai phạm vi `read` và `write`, và cung cấp các URL để lấy mã ủy quyền và token.

- **Tầm quan trọng**:  
  - Giúp nhà phát triển hiểu cách thiết lập bảo mật để sử dụng API an toàn.  
  - Đảm bảo rằng các yêu cầu bảo mật (như sử dụng token) được thực hiện đúng cách.  
  - Giảm nguy cơ sử dụng sai API dẫn đến các lỗ hổng bảo mật.

##### 12.1.4 Cung cấp tổng quan về API (Providing an Overview of the API)

- **Tổng quan API**:  
  Tài liệu tham khảo nên bao gồm một phần tổng quan để giới thiệu API, giải thích mục đích và các đặc điểm chính của nó. Trong OAS, phần này thường nằm trong `info.section`.  
  - Các yếu tố cần bao gồm:  
    - **Mô tả chung**: API làm gì và phục vụ mục đích gì?  
    - **Thông tin liên hệ**: Email hoặc URL hỗ trợ để người tiêu dùng liên hệ khi cần.  
    - **Phiên bản**: Phiên bản hiện tại của API.  

- **Ví dụ trong OAS**:  
  ```yaml
  info:
    title: API Quản lý Người dùng
    description: API này cho phép quản lý thông tin người dùng, bao gồm tạo, đọc, cập nhật, và xóa người dùng.
    version: 1.0.0
    contact:
      url: https://example.com/support
  ```
  Phần này cung cấp một cái nhìn tổng quan ngắn gọn, dễ hiểu về API.

- **Tầm quan trọng**:  
  - Giúp nhà phát triển nhanh chóng hiểu được API làm gì và phù hợp với nhu cầu của họ hay không.  
  - Cung cấp thông tin liên hệ để hỗ trợ khi cần thiết.

##### 12.1.5 Tạo tài liệu từ mã nguồn (Generating Documentation from Implementation)

- **Ưu điểm**:  
  - Một số framework (như Java Spring Boot) cho phép tạo tài liệu OAS từ mã nguồn, giúp tiết kiệm thời gian.  
  - Đảm bảo rằng tài liệu phản ánh đúng những gì được triển khai trong mã nguồn.  

- **Nhược điểm**:  
  - Tài liệu tạo tự động có thể thiếu mô tả chi tiết hoặc không rõ ràng, đặc biệt nếu chỉ dựa vào các chú thích (annotations).  
  - Ví dụ: Một chú thích trong mã nguồn có thể chỉ định rằng thuộc tính `type` chỉ nhận giá trị `checking` hoặc `savings`, nhưng không đảm bảo rằng mã nguồn thực sự tuân theo quy tắc này.  
  - Tài liệu tạo tự động thường chỉ tập trung vào cấu trúc (syntax) mà thiếu ngữ cảnh (context), làm cho tài liệu khó hiểu với người mới.  

- **Khuyến nghị**:  
  - Kết hợp tài liệu tạo tự động với chỉnh sửa thủ công để thêm các mô tả rõ ràng, ví dụ, và ngữ cảnh.  
  - Sử dụng các công cụ như **ReDoc** hoặc **Swagger UI** để hiển thị tài liệu OAS một cách trực quan và thân thiện với người dùng.

#### 12.2 Tạo hướng dẫn sử dụng (Creating a User Guide)

**Tổng quan**  
Hướng dẫn sử dụng bổ sung cho tài liệu tham khảo bằng cách cung cấp các hướng dẫn thực tế, giúp người tiêu dùng API áp dụng API vào các trường hợp sử dụng cụ thể. Nó tập trung vào cách sử dụng API thay vì chỉ mô tả cấu trúc.

##### 12.2.1 Tài liệu hóa các trường hợp sử dụng (Documenting Use Cases)

- **Mô tả các trường hợp sử dụng**:  
  Hướng dẫn sử dụng nên bao gồm các ví dụ thực tế về cách sử dụng API để đạt được các mục tiêu cụ thể.  
  - Ví dụ: Nếu API quản lý người dùng, một trường hợp sử dụng có thể là "Tạo một người dùng mới và lấy thông tin của họ".  
  - Mỗi trường hợp sử dụng nên bao gồm:  
    - **Mục tiêu**: Người dùng muốn đạt được gì?  
    - **Các bước**: Các lệnh gọi API cần thiết, bao gồm phương thức HTTP, đường dẫn, tham số, và phản hồi mong đợi.  
    - **Ví dụ mã nguồn**: Cung cấp đoạn mã (ví dụ: bằng cURL hoặc Python) để minh họa cách thực hiện lệnh gọi API.  

- **Ví dụ**:  
  Trường hợp sử dụng: Tạo một người dùng mới.  
  ```bash
  curl -X POST https://api.example.com/users \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer <token>" \
    -d '{"name": "Nguyen Van A", "email": "nguyenvana@example.com"}'
  ```
  Phản hồi:
  ```json
  {
    "id": "12345",
    "name": "Nguyen Van A",
    "email": "nguyenvana@example.com"
  }
  ```
  Sau đó, lấy thông tin người dùng:
  ```bash
  curl -X GET https://api.example.com/users/12345 \
    -H "Authorization: Bearer <token>"
  ```

- **Tầm quan trọng**:  
  - Giúp nhà phát triển nhanh chóng áp dụng API vào các tình huống thực tế.  
  - Giảm thời gian học hỏi bằng cách cung cấp các ví dụ cụ thể, dễ theo dõi.  
  - Tăng khả năng thành công khi tích hợp API.

##### 12.2.2 Tài liệu hóa bảo mật (Documenting Security)

- **Mô tả bảo mật trong hướng dẫn sử dụng**:  
  Hướng dẫn sử dụng cần giải thích cách thiết lập và sử dụng các cơ chế bảo mật của API, chẳng hạn như:  
  - **Đăng ký**: Làm thế nào để nhận được client ID và client secret?  
  - **Lấy token**: Quy trình lấy access token (ví dụ: sử dụng OAuth2).  
  - **Sử dụng token**: Cách thêm token vào các yêu cầu API (ví dụ: trong header `Authorization`).  

- **Ví dụ**:  
  Để lấy access token:
  ```bash
  curl -X POST https://example.com/oauth/token \
    -d "grant_type=client_credentials" \
    -d "client_id=<your_client_id>" \
    -d "client_secret=<your_client_secret>"
  ```
  Sử dụng token trong yêu cầu API:
  ```bash
  curl -X GET https://api.example.com/users \
    -H "Authorization: Bearer <access_token>"
  ```

- **Tầm quan trọng**:  
  - Đảm bảo rằng nhà phát triển hiểu cách bảo vệ API và sử dụng đúng các cơ chế bảo mật.  
  - Giảm nguy cơ lỗi bảo mật do sử dụng sai thông tin xác thực.

##### 12.2.3 Cung cấp tổng quan về các hành vi và nguyên tắc chung (Providing an Overview of Common Behaviors and Principles)

- **Mô tả các hành vi chung**:  
  Hướng dẫn sử dụng nên giải thích các nguyên tắc chung của API, chẳng hạn như:  
  - **Quy ước đặt tên**: Các tên tài nguyên và tham số có tuân theo một quy tắc cụ thể không?  
  - **Xử lý lỗi**: API trả về các mã lỗi (như 400, 404) như thế nào và ý nghĩa của chúng?  
  - **Phân trang (pagination)**: Cách API xử lý danh sách lớn (ví dụ: sử dụng `page` và `pagesize`).  
  - **Giới hạn tốc độ (rate limiting)**: Có giới hạn về số lượng yêu cầu trong một khoảng thời gian không?  

- **Ví dụ**:  
  API sử dụng phân trang với các tham số `page` và `pagesize`. Ví dụ:
  ```bash
  curl -X GET "https://api.example.com/users?page=2&pagesize=20" \
    -H "Authorization: Bearer <token>"
  ```

- **Tầm quan trọng**:  
  - Giúp nhà phát triển hiểu các mẫu hành vi chung của API, giảm thời gian tìm hiểu.  
  - Đảm bảo rằng nhà phát triển có thể dự đoán cách API hoạt động trong các tình huống khác nhau.

##### 12.2.4 Suy nghĩ vượt ra ngoài tài liệu tĩnh (Thinking Beyond Static Documentation)

- **Tài liệu động (Dynamic Documentation)**:  
  Thay vì chỉ cung cấp tài liệu tĩnh (PDF, trang web), nên sử dụng các công cụ như Swagger UI hoặc ReDoc để tạo tài liệu tương tác.  
  - **Swagger UI**: Cho phép nhà phát triển thử các lệnh gọi API trực tiếp từ trình duyệt.  
  - **ReDoc**: Hiển thị tài liệu OAS một cách đẹp mắt và dễ đọc.  

- **Tầm quan trọng**:  
  - Tài liệu tương tác giúp nhà phát triển thử nghiệm API mà không cần viết mã ngay lập tức.  
  - Tăng trải nghiệm người dùng và giảm rào cản khi bắt đầu sử dụng API.

#### 12.3 Cung cấp thông tin đầy đủ cho người triển khai (Providing Adequate Information to Implementers)

- **Thông tin cho người triển khai**:  
  Ngoài tài liệu cho người tiêu dùng API, cần cung cấp tài liệu cho những người triển khai API (nhà cung cấp). Điều này bao gồm:  
  - **Thông số kỹ thuật triển khai (Implementation Specifications)**: Mô tả các yêu cầu nội bộ, như cơ sở dữ liệu hoặc logic kinh doanh.  
  - **Hướng dẫn triển khai bảo mật**: Cách triển khai các cơ chế bảo mật (như OAuth2) trong mã nguồn.  
  - **Kiểm tra triển khai**: Các bài kiểm tra cần thiết để đảm bảo API hoạt động đúng như thiết kế.  

- **Ví dụ**:  
  Tài liệu cho người triển khai có thể bao gồm:  
  - Mô tả cách API kiểm tra tính hợp lệ của dữ liệu đầu vào.  
  - Yêu cầu về hiệu suất (ví dụ: thời gian phản hồi dưới 200ms).  
  - Cách xử lý lỗi trong mã nguồn (ví dụ: trả về mã 400 khi dữ liệu không hợp lệ).  

- **Tầm quan trọng**:  
  - Đảm bảo rằng đội ngũ triển khai hiểu rõ các yêu cầu thiết kế và có thể xây dựng API đúng với tài liệu.  
  - Giảm nguy cơ sai lệch giữa thiết kế và triển khai.

#### 12.4 Tài liệu hóa sự phát triển và ngừng hoạt động (Documenting Evolutions and Retirement)

- **Tài liệu hóa sự phát triển**:  
  Khi API được cập nhật (thêm tính năng mới, sửa lỗi, hoặc thay đổi giao diện), cần tài liệu hóa các thay đổi này.  
  - Sử dụng thuộc tính `deprecated` trong OAS để đánh dấu các thành phần không còn được khuyến nghị sử dụng.  
  - Ví dụ:
    ```yaml
    paths:
      /users/{id}:
        get:
          deprecated: true
          summary: Lấy thông tin người dùng (không khuyến nghị, sử dụng /v2/users/{id})
    ```

- **Tài liệu hóa ngừng hoạt động (Retirement)**:  
  Khi một API hoặc một phần của API bị ngừng hoạt động, cần thông báo rõ ràng cho người tiêu dùng.  
  - Sử dụng header `Sunset` để chỉ định thời điểm API sẽ ngừng hoạt động.  
  - Ví dụ:
    ```http
    Sunset: Wed, 15 Dec 2025 23:59:59 GMT
    ```
