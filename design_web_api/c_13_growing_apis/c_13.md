### Chương 13: Phát triển APIs (Growing APIs)

Chương 13 tập trung vào vai trò của các nhà thiết kế API trong việc đảm bảo rằng các API không chỉ được thiết kế tốt mà còn được quản lý và phát triển một cách hiệu quả trong suốt vòng đời của chúng. Nó nhấn mạnh tầm quan trọng của việc xây dựng hướng dẫn thiết kế API, xem xét (review) các thiết kế API, và chia sẻ kiến thức giữa các nhóm. Dưới đây là nội dung chi tiết của chương, được tổ chức theo các mục chính.

#### 13.1 Vòng đời API (The API Lifecycle)

**Tóm tắt nội dung:**
- Vòng đời API bao gồm các giai đoạn: phân tích (analyze), thiết kế (design), triển khai (implement), và xuất bản (publish).
- Nhà thiết kế API đóng vai trò trong tất cả các giai đoạn này, không chỉ giới hạn ở việc thiết kế giao diện lập trình (interface).
- Trong giai đoạn **phân tích**, nhà thiết kế API giúp xác định nhu cầu thực sự của API, đảm bảo rằng nó đáp ứng các yêu cầu của cả nhà cung cấp (provider) và người tiêu dùng (consumer).
- Trong giai đoạn **thiết kế**, họ tạo ra giao diện API dựa trên các yêu cầu đã xác định, sử dụng các công cụ như OpenAPI Specification (OAS).
- Trong giai đoạn **triển khai**, họ hỗ trợ đảm bảo rằng API được xây dựng đúng với thiết kế đã đề ra.
- Trong giai đoạn **xuất bản**, họ tham gia vào việc tài liệu hóa (documenting) và chia sẻ API với người tiêu dùng, bao gồm việc cung cấp hướng dẫn sử dụng và thông tin về các thay đổi hoặc ngừng hoạt động (retirement).

**Mục tiêu chính:**
- Đảm bảo rằng API được quản lý một cách nhất quán qua các giai đoạn của vòng đời.
- Nhà thiết kế API cần hợp tác với các nhóm khác (nhà phát triển, nhóm bảo mật, nhóm tài liệu) để đảm bảo sự thành công của API.

**Dịch sang tiếng Việt:**
- Vòng đời API bao gồm bốn giai đoạn chính: **phân tích**, **thiết kế**, **triển khai**, và **xuất bản**.
- Trong giai đoạn **phân tích**, nhà thiết kế API làm việc để hiểu rõ nhu cầu thực sự của API, đảm bảo rằng nó phù hợp với mục tiêu kinh doanh và kỹ thuật.
- Trong giai đoạn **thiết kế**, họ sử dụng các công cụ như OpenAPI Specification để định nghĩa giao diện API một cách rõ ràng và có cấu trúc.
- Trong giai đoạn **triển khai**, họ kiểm tra để đảm bảo rằng mã nguồn thực hiện đúng với thiết kế ban đầu.
- Trong giai đoạn **xuất bản**, họ giúp tạo tài liệu chi tiết, chia sẻ thông tin về API, và thông báo về bất kỳ thay đổi hoặc ngừng hoạt động nào.

#### 13.2 Xây dựng Hướng dẫn Thiết kế API (Building API Design Guidelines)

**Tóm tắt nội dung:**
- Hướng dẫn thiết kế API là tài liệu quan trọng để đảm bảo tính nhất quán (consistency) trong thiết kế API trên toàn tổ chức.
- Các hướng dẫn này giúp các nhà thiết kế API đưa ra quyết định phù hợp, tránh các sai lầm phổ biến, và duy trì sự thống nhất giữa các API khác nhau.

**Nội dung trong Hướng dẫn Thiết kế API (What to Put in API Design Guidelines):**
1. **Hướng dẫn quy trình thiết kế (Design Process Guidelines):**
   - Xác định cách xác định mục tiêu API (API goals), bao gồm việc sử dụng API goals canvas (trang 32).
   - Quy định cách sử dụng các công cụ như OpenAPI Specification để mô tả API.
   - Đưa ra các bước để xem xét và xác nhận thiết kế từ góc độ của nhà cung cấp và người tiêu dùng.

2. **Hướng dẫn tham chiếu (Reference Guidelines):**
   - Quy định cách đặt tên (naming conventions) cho các tài nguyên (resources), hành động (actions), và dữ liệu.
   - Quy định các kiểu dữ liệu (data types), định dạng (formats), và tiêu chuẩn (standards) như ISO 8601 cho ngày tháng hoặc E.164 cho số điện thoại.
   - Quy định cách sử dụng các phương thức HTTP (GET, POST, PUT, DELETE) và mã trạng thái HTTP (HTTP status codes).

**Xây dựng liên tục các hướng dẫn (Continuously Building Guidelines):**
- Hướng dẫn thiết kế API không phải là tài liệu tĩnh; chúng cần được cập nhật liên tục dựa trên kinh nghiệm thực tế và các tiêu chuẩn mới.
- Các nhà thiết kế API nên đóng góp vào việc cập nhật hướng dẫn bằng cách thêm các tiêu chuẩn mới (ví dụ: E.164 cho số điện thoại) và các bài học kinh nghiệm từ các dự án API trước đó.
- Sử dụng các công cụ như hệ thống kiểm soát mã nguồn (source control system) hoặc wiki để lưu trữ và chia sẻ hướng dẫn.

**Dịch sang tiếng Việt:**
- **Hướng dẫn thiết kế API** là tài liệu quan trọng để đảm bảo tất cả các API trong tổ chức được thiết kế một cách nhất quán.
- **Nội dung của hướng dẫn thiết kế API:**
  1. **Hướng dẫn quy trình thiết kế:**
     - Hướng dẫn cách xác định mục tiêu API bằng API goals canvas.
     - Quy định cách sử dụng OpenAPI Specification để mô tả API.
     - Đưa ra các bước để xem xét thiết kế từ góc độ của nhà cung cấp và người tiêu dùng.
  2. **Hướng dẫn tham chiếu:**
     - Quy định cách đặt tên cho tài nguyên, hành động, và dữ liệu.
     - Sử dụng các tiêu chuẩn như ISO 8601 (ngày tháng) hoặc E.164 (số điện thoại).
     - Quy định cách sử dụng các phương thức HTTP và mã trạng thái HTTP.
- **Xây dựng liên tục:**
  - Hướng dẫn cần được cập nhật thường xuyên dựa trên kinh nghiệm thực tế.
  - Các nhà thiết kế API đóng góp bằng cách thêm các tiêu chuẩn mới và bài học kinh nghiệm.
  - Lưu trữ hướng dẫn trên hệ thống kiểm soát mã nguồn hoặc wiki để dễ dàng truy cập và chia sẻ.

#### 13.3 Xem xét APIs (Reviewing APIs)

**Tóm tắt nội dung:**
- Việc xem xét (review) API là một bước quan trọng để đảm bảo rằng thiết kế API đáp ứng được nhu cầu của nhà cung cấp và người tiêu dùng, đồng thời tuân thủ các hướng dẫn thiết kế.
- Quá trình xem xét bao gồm năm bước chính: thách thức và phân tích nhu cầu, kiểm tra thiết kế (linting), xem xét từ góc độ nhà cung cấp, xem xét từ góc độ người tiêu dùng, và xác minh triển khai.

**13.3.1 Thách thức và Phân tích Nhu cầu (Challenging and Analyzing Needs):**
- Nhà thiết kế API cần thách thức các yêu cầu ban đầu để đảm bảo rằng API thực sự cần thiết và đáp ứng đúng mục tiêu.
- Sử dụng API goals canvas để xác định các mục tiêu (goals), đầu vào (inputs), đầu ra (outputs), và người dùng (users).
- Đảm bảo rằng API không chỉ là một giải pháp kỹ thuật mà còn giải quyết được vấn đề thực tế của người tiêu dùng.

**13.3.2 Kiểm tra Thiết kế (Linting the Design):**
- **Linting** là quá trình kiểm tra thiết kế API để đảm bảo rằng nó tuân thủ các hướng dẫn thiết kế và tiêu chuẩn.
- Kiểm tra các yếu tố như định dạng đường dẫn (path formats), mã trạng thái HTTP, và tính nhất quán với các API khác trong tổ chức.
- Sử dụng các công cụ tự động để kiểm tra các định dạng API máy có thể đọc được (machine-readable API description formats), nhưng vẫn cần sự can thiệp của con người để kiểm tra các yếu tố như mô tả dễ hiểu (human-readable descriptions).
- Đảm bảo rằng thiết kế sử dụng các tiêu chuẩn hiện có (ví dụ: ISO 8601, E.164) thay vì các định dạng tùy chỉnh (custom formats).
- Kiểm tra xem API có giới thiệu các thay đổi phá vỡ (breaking changes) khi phát triển API hiện có hay không.

**13.3.3 Xem xét Thiết kế từ Góc độ Nhà cung cấp (Reviewing the Design from the Provider’s Perspective):**
- Xác minh rằng thiết kế API đáp ứng tất cả các yêu cầu của nhà cung cấp, bao gồm:
  - Đáp ứng các mục tiêu đã xác định.
  - Đảm bảo tính bảo mật (secure), khả năng triển khai (implementable), và khả năng mở rộng (extensible).
  - Hiệu suất của các mục tiêu và luồng mục tiêu (goal flows) đáp ứng kỳ vọng.
- Sử dụng danh sách kiểm tra (checklist) dựa trên nội dung của sách để đánh giá (xem Hình 13.8 trong sách).
- Đảm bảo rằng tài liệu API hỗ trợ việc xem xét bằng cách cung cấp thông tin chi tiết về các mục tiêu, hành vi, và phản hồi (responses).

**13.3.4 Xem xét Thiết kế từ Góc độ Người tiêu dùng (Reviewing the Design from the Consumer’s Perspective):**
- Đánh giá API từ góc độ người tiêu dùng để đảm bảo rằng nó dễ sử dụng, dễ hiểu, và hiệu quả.
- Kiểm tra rằng các mục tiêu, tham số (parameters), và phản hồi (responses) không phản ánh góc độ của nhà cung cấp (provider’s perspective) một cách không cần thiết.
- Đảm bảo rằng các tham số bắt buộc là thực sự cần thiết và các mô tả sử dụng ngôn ngữ dễ hiểu, tránh thuật ngữ nội bộ (provider’s jargon).
- Đánh giá hiệu suất của các mục tiêu và luồng mục tiêu cho cả các trường hợp sử dụng cơ bản và phức tạp.
- Khuyến khích gửi thiết kế API cho các bên ngoài nhóm hoặc người tiêu dùng tiềm năng để nhận phản hồi.

**13.3.5 Xác minh Triển khai (Verifying the Implementation):**
- Kiểm tra rằng triển khai API thực sự tuân thủ hợp đồng giao diện (interface contract) đã thiết kế.
- Sử dụng các công cụ để tạo các bài kiểm tra (tests) dựa trên tệp mô tả API (API description files), nhưng cần bổ sung các bài kiểm tra thủ công để xác minh tất cả các hành vi dự kiến.
- **Lưu ý khi sử dụng tài liệu tạo tự động (Generated Documentation):**
  - Một số framework (như Java Spring Boot) cho phép tạo tệp mô tả API từ mã nguồn, nhưng cần kiểm tra rằng các giá trị khai báo (declarative values) trong mã thực sự khớp với hành vi thực tế.
  - Ví dụ: Nếu một thuộc tính được khai báo là chỉ có các giá trị “checking” và “savings”, cần kiểm tra rằng mã nguồn không trả về các giá trị khác.
- **Kiểm tra hợp đồng giao diện tại thời điểm chạy (Runtime):**
  - Kiểm tra các hành vi như mã trạng thái HTTP (ví dụ: 400 Bad Request) được trả về đúng như thiết kế.
  - Kiểm tra các thuộc tính bắt buộc (mandatory properties) và các giới hạn (minimum/maximum values, số lượng phần tử trong mảng).
- **Kiểm tra toàn bộ chuỗi mạng (Network Chain):**
  - Kiểm tra các yêu cầu API qua toàn bộ chuỗi mạng, bao gồm tường lửa (firewalls), proxy, và cổng API (API gateways).
  - Các lỗi phổ biến bao gồm tường lửa chặn các yêu cầu DELETE hoặc trả về các mã trạng thái sai (ví dụ: thay 5XX bằng 500 hoặc trả về trang HTML thay vì dữ liệu).

**Dịch sang tiếng Việt:**
- **Xem xét APIs** là bước quan trọng để đảm bảo thiết kế API chất lượng cao.
- **Thách thức và phân tích nhu cầu:**
  - Sử dụng API goals canvas để xác định mục tiêu, đầu vào, đầu ra, và người dùng.
  - Đảm bảo API giải quyết vấn đề thực tế của người tiêu dùng.
- **Kiểm tra thiết kế (Linting):**
  - Kiểm tra tính tuân thủ các hướng dẫn thiết kế, như định dạng đường dẫn và mã trạng thái HTTP.
  - Sử dụng công cụ tự động để kiểm tra định dạng máy đọc được, nhưng cần con người kiểm tra các mô tả dễ hiểu.
  - Kiểm tra việc sử dụng các tiêu chuẩn (ISO 8601, E.164) và tránh các thay đổi phá vỡ.
- **Xem xét từ góc độ nhà cung cấp:**
  - Đảm bảo API đáp ứng các yêu cầu, an toàn, khả thi, và có thể mở rộng.
  - Sử dụng danh sách kiểm tra để đánh giá hiệu suất và tính phù hợp.
- **Xem xét từ góc độ người tiêu dùng:**
  - Đảm bảo API dễ sử dụng, dễ hiểu, và hiệu quả.
  - Kiểm tra rằng các mục tiêu và phản hồi không sử dụng thuật ngữ nội bộ.
  - Nhận phản hồi từ người tiêu dùng tiềm năng để cải thiện thiết kế.
- **Xác minh triển khai:**
  - Kiểm tra rằng triển khai tuân thủ hợp đồng giao diện.
  - Sử dụng công cụ tạo bài kiểm tra, nhưng cần kiểm tra thủ công để đảm bảo hành vi đúng.
  - Kiểm tra toàn bộ chuỗi mạng để phát hiện lỗi từ tường lửa, proxy, hoặc cổng API.

#### 13.4 Giao tiếp và Chia sẻ (Communicating and Sharing)

**Tóm tắt nội dung:**
- Nhà thiết kế API không làm việc một mình mà cần hợp tác với nhiều bên: người tạo yêu cầu API, người tiêu dùng, nhà phát triển, nhóm bảo mật, và nhóm tài liệu.
- Để chia sẻ thiết kế API hiệu quả, cần:
  - Sử dụng định dạng mô tả API chuẩn (như OpenAPI Specification).
  - Lưu trữ tệp thiết kế trên hệ thống kiểm soát mã nguồn (như Git), wiki, hoặc cổng nhà phát triển (developer portal).
- Đảm bảo rằng các hướng dẫn thiết kế API và các mô hình dữ liệu (data models) dễ tìm và tra cứu (searchable).
- Khuyến khích cộng đồng nhà thiết kế API (API guild) để chia sẻ kiến thức và xem xét chéo (peer review) các thiết kế.
- Nhận phản hồi từ người tiêu dùng thực tế để cải thiện thiết kế.

**Dịch sang tiếng Việt:**
- Nhà thiết kế API cần hợp tác với nhiều bên liên quan để đảm bảo thành công.
- **Chia sẻ thiết kế API:**
  - Sử dụng định dạng chuẩn như OpenAPI Specification.
  - Lưu trữ thiết kế trên Git, wiki, hoặc cổng nhà phát triển.
- Đảm bảo hướng dẫn thiết kế và mô hình dữ liệu dễ truy cập và tra cứu.
- Xây dựng cộng đồng nhà thiết kế API để chia sẻ kinh nghiệm và xem xét chéo.
- Nhận phản hồi từ người tiêu dùng để cải thiện chất lượng thiết kế.

#### Tóm tắt (Summary)

- **Tài liệu hóa (Documentation):** Tài liệu là yếu tố quan trọng để thiết kế, xây dựng, và xác minh API.
- **Tính nhất quán (Consistency):** Không thể đạt được tính nhất quán nếu thiếu hướng dẫn thiết kế và tài liệu.
- **Hợp tác:** Thiết kế API không nên làm một mình; cần làm việc với các nhóm khác và xây dựng cộng đồng nhà thiết kế.
- **Vòng đời API:** Nhà thiết kế API tham gia vào toàn bộ vòng đời API, từ phân tích đến xuất bản.
- **Thách thức nhu cầu:** Nhà thiết kế cần phân tích sâu và thách thức các yêu cầu để đảm bảo API đáp ứng đúng mục tiêu.

**Dịch sang tiếng Việt:**
- **Tài liệu hóa:** Tài liệu là yếu tố cốt lõi để thiết kế, xây dựng, và xác minh API.
- **Tính nhất quán:** Cần có hướng dẫn thiết kế và tài liệu để đảm bảo tính nhất quán.
- **Hợp tác:** Thiết kế API là công việc nhóm; cần xây dựng cộng đồng nhà thiết kế để chia sẻ kiến thức.
- **Vòng đời API:** Nhà thiết kế tham gia vào tất cả các giai đoạn của vòng đời API.
- **Thách thức nhu cầu:** Phân tích và thách thức các yêu cầu để đảm bảo API thực sự hữu ích.

### Hướng dẫn học tập

Để nắm vững nội dung của Chương 13, bạn có thể thực hiện các bước sau:
1. **Đọc lại từng mục:** Đọc kỹ từng mục (13.1, 13.2, 13.3, 13.4) và ghi chú các điểm chính, đặc biệt là các khái niệm như vòng đời API, hướng dẫn thiết kế, và quy trình xem xét.
2. **Áp dụng thực tế:**
   - Tạo một API goals canvas cho một API giả định và sử dụng nó để xác định mục tiêu, đầu vào, đầu ra, và người dùng.
   - Thử viết một hướng dẫn thiết kế API đơn giản dựa trên các tiêu chuẩn như ISO 8601 hoặc E.164.
   - Thực hiện một bài tập “linting” bằng cách kiểm tra một thiết kế API mẫu (có thể sử dụng OpenAPI Specification) để đảm bảo tính nhất quán.
3. **Thảo luận và chia sẻ:** Tham gia vào một cộng đồng hoặc nhóm học tập để thảo luận về thiết kế API, chia sẻ ý tưởng, và nhận phản hồi.
4. **Kiểm tra triển khai:** Nếu có thể, sử dụng một công cụ như Postman để kiểm tra một API thực tế và xác minh rằng nó tuân thủ thiết kế đã đề ra.

Nếu bạn cần giải thích chi tiết hơn về bất kỳ phần nào hoặc muốn tôi cung cấp ví dụ cụ thể bằng tiếng Việt, hãy cho tôi biết!
