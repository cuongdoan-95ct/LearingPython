# Chương 11: Thiết kế một API trong bối cảnh

Chương này giải thích cách thiết kế một API trong bối cảnh cụ thể, xem xét các yếu tố như nhu cầu của người tiêu dùng API (consumer), mục tiêu kinh doanh, và các ràng buộc kỹ thuật. Một API không được thiết kế trong môi trường chân không; nó phải phù hợp với hệ sinh thái mà nó hoạt động, bao gồm các ứng dụng, người dùng, và cơ sở hạ tầng. Chương này nhấn mạnh tầm quan trọng của việc hiểu bối cảnh để tạo ra một API hữu ích, dễ sử dụng, và bền vững.

Nội dung chương được chia thành các phần chính sau:

1. **Hiểu bối cảnh của API** (Trang 275-281)

3. **Xử lý các ràng buộc trong bối cảnh** (Trang 291-300)
4. **Kiểm tra và tinh chỉnh thiết kế API** (Trang 300-305)

## 11.1 Hiểu bối cảnh của API (Trang 275-281)

### Đặt vấn đề (Setting the scene) - Trang 275-277

Để thiết kế một API hiệu quả, trước tiên cần hiểu bối cảnh mà API sẽ hoạt động. Hãy quay lại ví dụ về ứng dụng mạng xã hội được sử dụng xuyên suốt cuốn sách:

- **Ứng dụng mạng xã hội** có các chức năng như đăng bài, xem dòng thời gian (timeline), nhận thông báo, và quản lý hồ sơ người dùng.
- API hỗ trợ các chức năng này, chẳng hạn như:
  - `POST /posts`: Đăng bài viết mới.
  - `GET /timeline`: Lấy danh sách bài đăng trên dòng thời gian.
  - `GET /notifications`: Lấy thông báo của người dùng.
  - `GET /users/{id}`: Lấy thông tin hồ sơ người dùng.

**Bối cảnh** bao gồm:
- **Người tiêu dùng API**: Các ứng dụng di động, website, hoặc các hệ thống bên thứ ba (như đối tác tích hợp) sử dụng API.
- **Mục tiêu kinh doanh**: Tăng tương tác người dùng, cải thiện hiệu suất ứng dụng, hoặc mở rộng hệ sinh thái thông qua các đối tác.
- **Ràng buộc kỹ thuật**: Hạn chế về băng thông, khả năng mở rộng (scalability), bảo mật, hoặc tài nguyên máy chủ.
- **Người dùng cuối**: Những người sử dụng ứng dụng mạng xã hội, mong đợi trải nghiệm nhanh chóng, mượt mà, và đáng tin cậy.

Ví dụ: Nếu API được thiết kế cho ứng dụng di động chạy trên mạng 4G ở các khu vực nông thôn, thì cần ưu tiên giảm kích thước dữ liệu và số lượng yêu cầu mạng để đảm bảo hiệu suất tốt ngay cả trong điều kiện mạng yếu.

**Hình 11.1** (trong sách) minh họa bối cảnh của API mạng xã hội, với các thành phần như ứng dụng di động, website, backend, và các API bên thứ ba (như API nhận diện khuôn mặt hoặc lưu trữ ảnh). Hình này nhấn mạnh rằng API không hoạt động độc lập mà là một phần của hệ sinh thái lớn hơn.

### Xác định các yếu tố bối cảnh (Identifying the context elements) - Trang 277-281

Để hiểu bối cảnh, cần trả lời các câu hỏi sau:

1. **Ai là người tiêu dùng API?**
   - **Ứng dụng nội bộ**: Như ứng dụng di động hoặc website của công ty.
   - **Đối tác bên ngoài**: Các công ty tích hợp API để cung cấp tính năng bổ sung (ví dụ: một ứng dụng chỉnh sửa ảnh tích hợp với API mạng xã hội để đăng bài trực tiếp).
   - **Nhà phát triển bên thứ ba**: Những người sử dụng API công khai để xây dựng ứng dụng mới.
   - **Ví dụ**: API `/timeline` có thể được sử dụng bởi ứng dụng di động nội bộ, nhưng cũng có thể được mở rộng cho các đối tác để hiển thị bài đăng trên các nền tảng khác.

2. **API phục vụ mục tiêu kinh doanh nào?**
   - Tăng tương tác người dùng (như khuyến khích đăng bài thường xuyên).
   - Tạo doanh thu (như cung cấp API trả phí cho đối tác).
   - Mở rộng hệ sinh thái (như cho phép các ứng dụng bên thứ ba tích hợp).
   - **Ví dụ**: API `/notifications` được thiết kế để gửi thông báo theo thời gian thực, tăng khả năng người dùng quay lại ứng dụng.

3. **API hoạt động trong môi trường nào?**
   - **Mạng**: Mạng di động (3G, 4G, 5G), Wi-Fi, hoặc mạng nội bộ (intranet).
   - **Thiết bị**: Điện thoại thông minh, máy tính bảng, máy tính để bàn, hoặc thiết bị IoT.
   - **Hệ điều hành**: iOS, Android, Windows, hoặc Linux.
   - **Ví dụ**: Ứng dụng di động chạy trên Android ở khu vực có mạng chậm sẽ yêu cầu API tối ưu hóa dữ liệu và giảm độ trễ.

4. **Có những ràng buộc nào?**
   - **Kỹ thuật**: Hạn chế về tài nguyên máy chủ, băng thông, hoặc khả năng xử lý.
   - **Pháp lý**: Tuân thủ các quy định như GDPR (bảo vệ dữ liệu cá nhân) hoặc CCPA.
   - **Bảo mật**: Đảm bảo dữ liệu nhạy cảm (như thông tin người dùng) được bảo vệ.
   - **Ví dụ**: API `/users/{id}` phải tuân thủ GDPR, chỉ trả về dữ liệu cá nhân khi có sự đồng ý của người dùng.

5. **Người dùng cuối mong đợi gì?**
   - Trải nghiệm nhanh chóng, đáng tin cậy, và dễ sử dụng.
   - **Ví dụ**: Người dùng mong đợi dòng thời gian tải ngay lập tức khi mở ứng dụng, ngay cả trên mạng yếu.

**Bảng 11.1** (trong sách) liệt kê các yếu tố bối cảnh và ví dụ tương ứng, giúp người thiết kế API lập danh sách kiểm tra (checklist) để đảm bảo không bỏ sót yếu tố nào.

## 11.2 Thiết kế API dựa trên nhu cầu người tiêu dùng (Trang 281-291)

Phần này nhấn mạnh rằng thiết kế API phải bắt đầu từ nhu cầu của người tiêu dùng, thay vì chỉ tập trung vào khả năng kỹ thuật của hệ thống backend.

### Hiểu nhu cầu của người tiêu dùng (Understanding consumer needs) - Trang 281-285

1. **Thu thập thông tin từ người tiêu dùng**:
   - **Phỏng vấn**: Nói chuyện trực tiếp với các nhà phát triển hoặc đối tác sử dụng API để hiểu nhu cầu của họ.
   - **Khảo sát**: Gửi bảng câu hỏi để thu thập phản hồi về các tính năng mong muốn.
   - **Phân tích hành vi**: Quan sát cách người tiêu dùng hiện tại sử dụng API (nếu API đã tồn tại).
   - **Ví dụ**: Các nhà phát triển ứng dụng di động có thể yêu cầu API `/timeline` trả về dữ liệu tối giản (như `id`, `content`, `user.name`) để giảm tải mạng.

2. **Xác định trường hợp sử dụng (use cases)**:
   - Mỗi người tiêu dùng có thể có trường hợp sử dụng khác nhau. Ví dụ:
     - Ứng dụng di động cần dữ liệu dòng thời gian theo thời gian thực.
     - Đối tác bên thứ ba cần dữ liệu bài đăng để phân tích xu hướng.
   - **Cách thực hiện**: Lập danh sách các trường hợp sử dụng và ưu tiên chúng dựa trên mức độ quan trọng hoặc tần suất sử dụng.
   - **Ví dụ**: Trường hợp sử dụng chính của API `/timeline` là hiển thị bài đăng cho người dùng cuối, nhưng cũng có thể hỗ trợ phân tích dữ liệu cho đối tác.

3. **Thiết kế dựa trên trải nghiệm nhà phát triển (Developer Experience - DX)**:
   - API phải dễ hiểu, dễ sử dụng, và có tài liệu rõ ràng.
   - **Ví dụ**: Cung cấp tài liệu API với các ví dụ mã nguồn (code samples) cho các ngôn ngữ phổ biến như JavaScript, Python, hoặc Swift.

**Hình 11.2** minh họa quy trình thu thập nhu cầu, từ phỏng vấn đến phân tích trường hợp sử dụng, để đảm bảo API đáp ứng đúng mong đợi của người tiêu dùng.

### Tạo các điểm cuối phù hợp (Creating suitable endpoints) - Trang 285-288

Dựa trên nhu cầu, thiết kế các điểm cuối (endpoints) đáp ứng chính xác yêu cầu của người tiêu dùng:

1. **Điểm cuối cụ thể (Specific endpoints)**:
   - Tạo các điểm cuối tập trung vào một trường hợp sử dụng cụ thể. Ví dụ:
     - `GET /timeline`: Lấy danh sách bài đăng trên dòng thời gian.
     - `GET /timeline/trending`: Lấy các bài đăng đang thịnh hành.
   - **Lợi ích**: Giảm sự phức tạp cho người tiêu dùng, chỉ cung cấp dữ liệu họ cần.

2. **Tham số linh hoạt (Flexible parameters)**:
   - Cho phép người tiêu dùng tùy chỉnh dữ liệu trả về thông qua tham số truy vấn. Ví dụ:
     - `GET /timeline?fields=id,content,user.name`: Chỉ trả về các trường được yêu cầu.
     - `GET /timeline?sort=recent`: Sắp xếp bài đăng theo thời gian gần nhất.
   - **Lợi ích**: Tăng tính linh hoạt mà không cần tạo nhiều điểm cuối mới.

3. **Tổng hợp dữ liệu (Data aggregation)**:
   - Gộp dữ liệu từ nhiều nguồn vào một điểm cuối để giảm số lượng yêu cầu. Ví dụ:
     - `GET /timeline?include=user,comments`: Trả về bài đăng cùng với thông tin người dùng và bình luận.
   - **Lợi ích**: Giảm độ trễ và cải thiện hiệu suất.

**Ví dụ**: Một ứng dụng di động yêu cầu dữ liệu dòng thời gian với thông tin người dùng và bình luận. Thay vì gửi ba yêu cầu riêng (`GET /timeline`, `GET /users/{id}`, `GET /posts/{id}/comments`), API cung cấp `GET /timeline?include=user,comments` để trả về tất cả trong một phản hồi.

### Đảm bảo tính nhất quán (Ensuring consistency) - Trang 288-291

Một API tốt không chỉ đáp ứng nhu cầu mà còn phải nhất quán để dễ sử dụng:

1. **Cấu trúc dữ liệu nhất quán**:
   - Sử dụng cùng một định dạng cho các trường dữ liệu tương tự. Ví dụ:
     - Trường `user_id` luôn là số nguyên (integer) trong mọi điểm cuối.
     - Trường `created_at` luôn sử dụng định dạng ISO 8601 (như `2025-06-15T09:40:00Z`).
   - **Lợi ích**: Giảm thời gian học cách sử dụng API.

2. **Quy ước đặt tên (Naming conventions)**:
   - Sử dụng quy tắc đặt tên rõ ràng và nhất quán. Ví dụ:
     - Sử dụng danh từ số nhiều cho tài nguyên (như `/posts` thay vì `/post`).
     - Sử dụng động từ cho hành động (như `/posts/{id}/like` để thích bài đăng).
   - **Lợi ích**: Giúp nhà phát triển dễ đoán cách sử dụng các điểm cuối khác.

3. **Mã trạng thái HTTP nhất quán**:
   - Sử dụng mã trạng thái HTTP tiêu chuẩn:
     - `200 OK`: Yêu cầu thành công.
     - `201 Created`: Tài nguyên được tạo.
     - `400 Bad Request`: Yêu cầu không hợp lệ.
     - `404 Not Found`: Tài nguyên không tồn tại.
   - **Lợi ích**: Giúp người tiêu dùng xử lý phản hồi dễ dàng hơn.

**Bảng 11.2** liệt kê các ví dụ về cấu trúc dữ liệu, quy ước đặt tên, và mã trạng thái để đảm bảo tính nhất quán trong thiết kế API.

## 11.3 Xử lý các ràng buộc trong bối cảnh (Trang 291-300)

Phần này thảo luận cách xử lý các ràng buộc kỹ thuật, pháp lý, và tổ chức khi thiết kế API.

### Xử lý các ràng buộc kỹ thuật (Handling technical constraints) - Trang 291-295

1. **Hiệu suất (Performance)**:
   - **Ràng buộc**: Máy chủ có thể bị quá tải nếu nhiều người dùng truy cập API cùng lúc.
   - **Giải pháp**:
     - Sử dụng phân trang (pagination) để giới hạn số lượng dữ liệu trả về. Ví dụ: `GET /timeline?page=1&pagesize=10`.
     - Kích hoạt lưu trữ tạm thời (caching) với tiêu đề `Cache-Control`.
     - Sử dụng nén dữ liệu (như Gzip hoặc Brotli) để giảm kích thước phản hồi.
   - **Ví dụ**: API `/timeline` sử dụng `Cache-Control: max-age=60` để lưu trữ dữ liệu trong 60 giây, giảm tải cho máy chủ.

2. **Khả năng mở rộng (Scalability)**:
   - **Ràng buộc**: API phải xử lý hàng triệu yêu cầu mỗi giây khi ứng dụng phát triển.
   - **Giải pháp**:
     - Sử dụng kiến trúc phân tán (distributed architecture) với các dịch vụ như CDN (Content Delivery Network).
     - Tối ưu hóa cơ sở dữ liệu bằng cách sử dụng chỉ mục (indexes) hoặc cơ sở dữ liệu NoSQL.
   - **Ví dụ**: API `/posts` sử dụng MongoDB để lưu trữ bài đăng, cho phép truy vấn nhanh ngay cả với dữ liệu lớn.

3. **Tài nguyên thiết bị (Device resources)**:
   - **Ràng buộc**: Thiết bị di động có hạn chế về CPU, pin, và băng thông.
   - **Giải pháp**:
     - Giảm kích thước dữ liệu bằng cách cho phép lọc trường (`fields`).
     - Sử dụng định dạng dữ liệu nhẹ như JSON thay vì XML.
   - **Ví dụ**: Ứng dụng di động chỉ yêu cầu `GET /timeline?fields=id,content` để tiết kiệm băng thông.

### Xử lý các ràng buộc pháp lý (Handling legal constraints) - Trang 295-297

1. **Bảo vệ dữ liệu cá nhân**:
   - **Ràng buộc**: Các quy định như GDPR yêu cầu bảo vệ dữ liệu cá nhân và chỉ chia sẻ khi có sự đồng ý.
   - **Giải pháp**:
     - Chỉ trả về dữ liệu cá nhân khi được yêu cầu rõ ràng (như thông qua tham số `fields`).
     - Sử dụng mã hóa (encryption) cho dữ liệu nhạy cảm trong quá trình truyền (HTTPS).
     - Cung cấp cơ chế xóa dữ liệu (như `DELETE /users/{id}/data`) để tuân thủ quyền "được lãng quên".
   - **Ví dụ**: API `/users/{id}` chỉ trả về `email` nếu người dùng đã đồng ý chia sẻ.

2. **Tuân thủ bản quyền**:
   - **Ràng buộc**: Nội dung do người dùng đăng (như ảnh hoặc video) phải tuân thủ luật bản quyền.
   - **Giải pháp**:
     - Tích hợp API bên thứ ba để kiểm tra bản quyền trước khi lưu trữ nội dung.
     - Cung cấp điểm cuối để báo cáo vi phạm (như `POST /reports`).
   - **Ví dụ**: API `/posts` kiểm tra ảnh tải lên bằng API nhận diện bản quyền trước khi lưu.

### Xử lý các ràng buộc tổ chức (Handling organizational constraints) - Trang 297-300

1. **Phân chia trách nhiệm**:
   - **Ràng buộc**: Nhiều nhóm trong công ty (như nhóm di động, nhóm web, nhóm backend) có thể có yêu cầu khác nhau đối với API.
   - **Giải pháp**:
     - Tổ chức các cuộc họp giữa các nhóm để thống nhất yêu cầu.
     - Sử dụng tài liệu API (như OpenAPI/Swagger) để làm rõ cách API hoạt động.
   - **Ví dụ**: Nhóm di động yêu cầu dữ liệu tối giản, trong khi nhóm web cần dữ liệu chi tiết hơn. API `/timeline` hỗ trợ cả hai bằng tham số `fields`.

2. **Ngân sách và thời gian**:
   - **Ràng buộc**: Công ty có thể có ngân sách hoặc thời gian hạn chế để phát triển API.
   - **Giải pháp**:
     - Ưu tiên các tính năng quan trọng nhất dựa trên nhu cầu người tiêu dùng.
     - Tái sử dụng các thành phần hiện có (như thư viện hoặc API bên thứ ba).
   - **Ví dụ**: Thay vì xây dựng API nhận diện khuôn mặt, công ty sử dụng API công khai từ bên thứ ba để tiết kiệm thời gian.

**Hình 11.3** minh họa cách các ràng buộc kỹ thuật, pháp lý, và tổ chức ảnh hưởng đến thiết kế API. Ví dụ: Một API phải cân bằng giữa hiệu suất (giảm độ trễ), bảo mật (mã hóa dữ liệu), và chi phí phát triển (tái sử dụng tài nguyên).

---

## 11.4 Kiểm tra và tinh chỉnh thiết kế API (Trang 300-305)

Sau khi thiết kế API, cần kiểm tra và tinh chỉnh để đảm bảo nó đáp ứng bối cảnh và nhu cầu.

### Kiểm tra API (Testing the API) - Trang 300-302

1. **Kiểm tra chức năng (Functional testing)**:
   - Đảm bảo API hoạt động đúng như tài liệu. Ví dụ:
     - `GET /timeline` trả về danh sách bài đăng đúng định dạng.
     - `POST /posts` tạo bài đăng mới và trả về mã trạng thái `201 Created`.
   - **Cách thực hiện**: Sử dụng các công cụ như Postman hoặc cURL để gửi yêu cầu thử nghiệm.

2. **Kiểm tra hiệu suất (Performance testing)**:
   - Đánh giá thời gian phản hồi và khả năng xử lý tải lớn. Ví dụ:
     - API `/timeline` có thể xử lý 10.000 yêu cầu mỗi giây không?
     - Phản hồi có kích thước nhỏ hơn 100 KB khi sử dụng nén không?
   - **Cách thực hiện**: Sử dụng công cụ như JMeter hoặc Locust để mô phỏng lưu lượng truy cập.

3. **Kiểm tra bảo mật (Security testing)**:
   - Kiểm tra các lỗ hổng như SQL injection, XSS, hoặc rò rỉ dữ liệu.
   - **Cách thực hiện**: Sử dụng công cụ như OWASP ZAP hoặc Burp Suite.

**Bảng 11.3** liệt kê các loại kiểm tra và công cụ đề xuất để đảm bảo chất lượng API.

### Thu thập phản hồi (Gathering feedback) - Trang 302-304

1. **Phản hồi từ người tiêu dùng**:
   - Sau khi triển khai API, thu thập ý kiến từ các nhà phát triển hoặc đối tác sử dụng API.
   - **Cách thực hiện**:
     - Cung cấp kênh hỗ trợ (như email hoặc diễn đàn).
     - Theo dõi lỗi hoặc yêu cầu tính năng mới thông qua hệ thống như Jira.
   - **Ví dụ**: Nhà phát triển báo rằng `GET /timeline` trả về quá nhiều dữ liệu, dẫn đến đề xuất thêm tham số `fields`.

2. **Phân tích sử dụng (Usage analytics)**:
   - Theo dõi cách API được sử dụng để xác định các điểm cần cải thiện. Ví dụ:
     - Điểm cuối nào được gọi nhiều nhất?
     - Có yêu cầu nào bị lỗi thường xuyên không?
   - **Cách thực hiện**: Sử dụng công cụ như Grafana hoặc New Relic để phân tích lưu lượng truy cập.

### Tinh chỉnh thiết kế (Refining the design) - Trang 304-305

Dựa trên kết quả kiểm tra và phản hồi, tinh chỉnh API để cải thiện:

1. **Cải thiện hiệu suất**:
   - Thêm lưu trữ tạm thời hoặc tối ưu hóa truy vấn cơ sở dữ liệu nếu thời gian phản hồi chậm.
   - **Ví dụ**: Tối ưu hóa `GET /timeline` bằng cách sử dụng chỉ mục cơ sở dữ liệu.

2. **Tăng tính linh hoạt**:
   - Thêm tham số mới hoặc điểm cuối để đáp ứng các trường hợp sử dụng mới.
   - **Ví dụ**: Thêm `GET /timeline?filter=friends` để chỉ lấy bài đăng từ bạn bè.

3. **Cải thiện tài liệu**:
   - Cập nhật tài liệu API với các ví dụ mới hoặc giải thích rõ hơn.
   - **Ví dụ**: Thêm ví dụ mã nguồn cho `GET /timeline?fields=id,content` trong tài liệu.

**Hình 11.4** minh họa vòng lặp kiểm tra-phản hồi-tinh chỉnh, nhấn mạnh rằng thiết kế API là một quá trình lặp lại (iterative process).

## Tóm tắt nội dung chính của Chương 11

- **Hiểu bối cảnh**:
  - Xác định người tiêu dùng API, mục tiêu kinh doanh, môi trường hoạt động, ràng buộc, và mong đợi của người dùng cuối.
  - Bối cảnh quyết định cách API được thiết kế để phù hợp với hệ sinh thái.

- **Thiết kế dựa trên nhu cầu người tiêu dùng**:
  - Thu thập thông tin từ nhà phát triển, xác định trường hợp sử dụng, và tạo các điểm cuối phù hợp.
  - Đảm bảo tính nhất quán trong cấu trúc dữ liệu, quy ước đặt tên, và mã trạng thái HTTP.

- **Xử lý ràng buộc**:
  - Tối ưu hóa hiệu suất, khả năng mở rộng, và tài nguyên thiết bị.
  - Tuân thủ các quy định pháp lý như GDPR và xử lý các ràng buộc tổ chức như ngân sách hoặc phân chia trách nhiệm.

- **Kiểm tra và tinh chỉnh**:
  - Thực hiện kiểm tra chức năng, hiệu suất, và bảo mật.
  - Thu thập phản hồi từ người tiêu dùng và phân tích sử dụng để cải thiện API.
  - Tinh chỉnh thiết kế để tăng hiệu quả và đáp ứng các nhu cầu mới.
