**## Chapter 3: Thiết Kế Giao Diện Lập Trình (Designing a Programming Interface)

Chương này bao gồm:

- Giới thiệu về API REST
- Chuyển đổi mục tiêu API thành API REST
- Thiết kế dữ liệu của API
- Tìm kiếm sự cân bằng khi đối mặt với các thách thức thiết kế
- Hiểu tại sao REST quan trọng đối với thiết kế của bất kỳ API nào

Sau khi xác định các mục tiêu của API (như được thảo luận trong Chương 2), bước tiếp theo là chuyển đổi chúng thành một giao diện lập trình – một API thực sự. Trong chương này, chúng ta sẽ tập trung vào API REST, sử dụng chúng như một ví dụ để làm sáng tỏ các nguyên tắc thiết kế API. Bạn sẽ học cách thiết kế một giao diện lập trình dựa trên các mục tiêu đã xác định, bao gồm các tài nguyên, hành động trên tài nguyên, dữ liệu, tham số và phản hồi. Ngoài ra, bạn sẽ khám phá lý do tại sao phong cách kiến trúc REST lại quan trọng đối với bất kỳ thiết kế API nào, ngay cả khi bạn không sử dụng API REST.

### 3.1 Giới Thiệu về API REST (Introducing REST APIs)

API REST là một loại API web phổ biến, sử dụng giao thức HTTP để cho phép các ứng dụng giao tiếp với nhau. Để hiểu rõ cách thiết kế một API REST, trước tiên chúng ta cần phân tích một lời gọi API REST và làm quen với các nguyên tắc cơ bản của HTTP và REST.

#### 3.1.1 Phân Tích Một Lời Gọi API REST (Analyzing a REST API Call)

Hãy xem xét một ví dụ về một lời gọi API REST đơn giản để lấy thông tin về một người dùng từ một ứng dụng mạng xã hội. Giả sử bạn muốn lấy thông tin chi tiết về một người dùng cụ thể, chẳng hạn như tên và địa chỉ email của họ. Lời gọi API có thể trông như sau:

```
GET /users/123
```

- **GET**: Đây là phương thức HTTP, chỉ ra rằng chúng ta muốn truy xuất dữ liệu.
- **/users/123**: Đây là đường dẫn tài nguyên, xác định tài nguyên cụ thể (người dùng có ID là 123) mà chúng ta muốn truy xuất.
- **Phản hồi**: Máy chủ có thể trả về một phản hồi JSON như sau:

```json
{
  "id": "123",
  "name": "John Doe",
  "email": "john.doe@example.com"
}
```

Lời gọi này minh họa cách một API REST hoạt động: một ứng dụng khách (client) gửi yêu cầu đến máy chủ (server) bằng HTTP, và máy chủ trả về dữ liệu ở định dạng có cấu trúc (thường là JSON). Phần thân phản hồi chứa dữ liệu được yêu cầu, trong trường hợp này là thông tin chi tiết về người dùng.

#### 3.1.2 Nguyên Tắc Cơ Bản của HTTP (Basic Principles of HTTP)

HTTP (Giao thức Truyền Siêu văn bản) là nền tảng của các API web, bao gồm cả API REST. Dưới đây là một số nguyên tắc cơ bản của HTTP:

- **Phương thức HTTP**: Các phương thức như GET, POST, PUT, DELETE, PATCH xác định hành động được thực hiện trên tài nguyên. Ví dụ:
  - GET: Truy xuất dữ liệu.
  - POST: Tạo tài nguyên mới.
  - PUT: Cập nhật tài nguyên hiện có.
  - DELETE: Xóa tài nguyên.
- **Mã trạng thái HTTP**: Các mã như 200 OK, 404 Not Found, 400 Bad Request chỉ ra kết quả của yêu cầu. Ví dụ:
  - 200 OK: Yêu cầu thành công.
  - 404 Not Found: Tài nguyên không được tìm thấy.
- **Tiêu đề HTTP**: Cung cấp siêu dữ liệu về yêu cầu hoặc phản hồi, chẳng hạn như Content-Type (định dạng dữ liệu) hoặc Authorization (xác thực).
- **Phần thân yêu cầu/phản hồi**: Chứa dữ liệu được gửi hoặc nhận, thường ở định dạng JSON hoặc XML.

Hiểu các nguyên tắc này rất quan trọng vì API REST dựa vào chúng để xác định các tương tác giữa ứng dụng khách và máy chủ.

#### 3.1.3 Nguyên Tắc Cơ Bản của API REST (Basic Principles of REST APIs)

API REST tuân theo phong cách kiến trúc REST (Representational State Transfer), được định nghĩa bởi Roy Fielding. Các nguyên tắc chính bao gồm:

- **Tài nguyên (Resources)**: Mọi thứ trong API REST đều được biểu diễn dưới dạng tài nguyên, chẳng hạn như "người dùng", "bài đăng", hoặc "bình luận". Các tài nguyên được xác định bằng URI (Uniform Resource Identifier), ví dụ: `/users/123`.
- **Phương thức HTTP**: Sử dụng các phương thức HTTP tiêu chuẩn để thực hiện các hành động trên tài nguyên (GET để lấy, POST để tạo, v.v.).
- **Không trạng thái (Stateless)**: Mỗi yêu cầu từ ứng dụng khách đến máy chủ phải chứa tất cả thông tin cần thiết để xử lý yêu cầu. Máy chủ không lưu trữ trạng thái giữa các yêu cầu.
- **Khả năng lưu trữ (Cacheability)**: Phản hồi từ máy chủ có thể được lưu trữ để cải thiện hiệu suất.
- **Phân tầng (Layered System)**: Hệ thống có thể bao gồm nhiều lớp (ví dụ: proxy, cổng API) mà không ảnh hưởng đến ứng dụng khách.
- **Truyền trạng thái biểu diễn (Representational State Transfer)**: Dữ liệu được truyền dưới dạng biểu diễn (thường là JSON hoặc XML) của trạng thái tài nguyên.

Những nguyên tắc này đảm bảo rằng API REST dễ mở rộng, đáng tin cậy và dễ sử dụng.

### 3.2 Chuyển Đổi Mục Tiêu API Thành API REST (Transposing API Goals into a REST API)

Sau khi xác định các mục tiêu của API (sử dụng canvas mục tiêu API, như được thảo luận trong Chương 2), bước tiếp theo là ánh xạ chúng thành một API REST. Quá trình này bao gồm việc xác định tài nguyên, hành động, đường dẫn và phương thức HTTP.

#### 3.2.1 Xác Định Tài Nguyên và Mối Quan Hệ của Chúng với Canvas Mục Tiêu API (Identifying Resources and Their Relationships with the API Goals Canvas)

Canvas mục tiêu API giúp xác định các mục tiêu của API bằng cách trả lời các câu hỏi: *Cái gì?*, *Ai?*, *Như thế nào?*, *Nguồn đầu vào?*, và *Đầu ra?*. Để chuyển đổi các mục tiêu này thành API REST, trước tiên chúng ta cần xác định các tài nguyên.

Ví dụ, giả sử canvas mục tiêu API bao gồm mục tiêu sau:

- **Cái gì**: Lấy thông tin chi tiết về người dùng.
- **Ai**: Ứng dụng di động.
- **Như thế nào**: Truy xuất dữ liệu người dùng dựa trên ID.
- **Nguồn đầu vào**: ID người dùng.
- **Đầu ra**: Tên, email, ngày sinh.

Từ mục tiêu này, chúng ta có thể xác định:

- **Tài nguyên**: Người dùng (`users`).
- **Tài nguyên cụ thể**: Một người dùng cụ thể (`users/{id}`).

Mối quan hệ giữa các tài nguyên cũng cần được xem xét. Ví dụ, nếu ứng dụng mạng xã hội cho phép người dùng có bài đăng, chúng ta có thể có tài nguyên `/posts` và một mối quan hệ với `/users/{id}/posts` để lấy tất cả bài đăng của một người dùng cụ thể.

#### 3.2.2 Xác Định Hành Động và Tham Số/Phản Hồi của Chúng với Canvas Mục Tiêu API (Identifying Actions and Their Parameters and Returns with the API Goals Canvas)

Tiếp theo, chúng ta ánh xạ các hành động từ mục tiêu API thành các phương thức HTTP và xác định các tham số cũng như phản hồi.

Dựa trên ví dụ trên:

- **Hành động**: Lấy thông tin người dùng.
- **Phương thức HTTP**: GET.
- **Đường dẫn**: `/users/{id}`.
- **Tham số**: ID người dùng (trong đường dẫn).
- **Phản hồi**: Một đối tượng JSON chứa tên, email, và ngày sinh.

Ví dụ yêu cầu:

```
GET /users/123
```

Phản hồi:

```json
{
  "id": "123",
  "name": "John Doe",
  "email": "john.doe@example.com",
  "birthdate": "1990-01-01"
}
```

Nếu mục tiêu API bao gồm việc tạo một người dùng mới, chúng ta có thể có:

- **Hành động**: Tạo người dùng.
- **Phương thức HTTP**: POST.
- **Đường dẫn**: `/users`.
- **Tham số**: Tên, email, ngày sinh (trong phần thân yêu cầu).
- **Phản hồi**: Thông tin người dùng đã tạo và mã trạng thái 201 Created.

Ví dụ yêu cầu:

```
POST /users
Content-Type: application/json

{
  "name": "Jane Smith",
  "email": "jane.smith@example.com",
  "birthdate": "1995-05-10"
}
```

Phản hồi:

```json
{
  "id": "124",
  "name": "Jane Smith",
  "email": "jane.smith@example.com",
  "birthdate": "1995-05-10"
}
```

#### 3.2.3 Biểu Diễn Tài Nguyên bằng Đường Dẫn (Representing Resources with Paths)

Đường dẫn trong API REST được sử dụng để xác định tài nguyên. Một số nguyên tắc để chọn đường dẫn tài nguyên:

- **Sử dụng danh từ**: Đường dẫn nên đại diện cho tài nguyên (ví dụ: `/users`, `/posts`), không phải hành động (tránh `/getUsers`).
- **Phân cấp**: Sử dụng cấu trúc phân cấp để biểu thị mối quan hệ (ví dụ: `/users/{id}/posts`).
- **Đơn giản và rõ ràng**: Đường dẫn nên dễ hiểu và nhất quán.

Ví dụ, để lấy danh sách tất cả người dùng:

```
GET /users
```

Để lấy một người dùng cụ thể:

```
GET /users/123
```

Để lấy bài đăng của một người dùng:

```
GET /users/123/posts
```

#### 3.2.4 Biểu Diễn Hành Động bằng HTTP (Representing Actions with HTTP)

Các phương thức HTTP được sử dụng để biểu diễn các hành động trên tài nguyên. Bảng dưới đây tóm tắt các ánh xạ phổ biến:

| Hành động         | Phương thức HTTP | Đường dẫn           | Mô tả                              |
|-------------------|------------------|---------------------|------------------------------------|
| Lấy danh sách     | GET              | `/users`            | Lấy tất cả người dùng             |
| Lấy chi tiết      | GET              | `/users/{id}`       | Lấy một người dùng cụ thể         |
| Tạo               | POST             | `/users`            | Tạo một người dùng mới            |
| Cập nhật          | PUT hoặc PATCH   | `/users/{id}`       | Cập nhật thông tin người dùng     |
| Xóa               | DELETE           | `/users/{id}`       | Xóa một người dùng               |

Ví dụ, để cập nhật thông tin người dùng:

```
PUT /users/123
Content-Type: application/json

{
  "name": "John Smith",
  "email": "john.smith@example.com",
  "birthdate": "1990-01-01"
}
```

Phản hồi:

```json
{
  "id": "123",
  "name": "John Smith",
  "email": "john.smith@example.com",
  "birthdate": "1990-01-01"
}
```

#### 3.2.5 Bảng Tóm Tắt API REST và HTTP (REST API and HTTP Cheat Sheet)

Dưới đây là bảng tóm tắt để tham khảo nhanh:

| Phương thức | Đường dẫn            | Mã trạng thái | Mô tả                              |
|-------------|----------------------|---------------|------------------------------------|
| GET         | `/resources`         | 200 OK        | Lấy danh sách tài nguyên          |
| GET         | `/resources/{id}`    | 200 OK        | Lấy một tài nguyên cụ thể         |
| POST        | `/resources`         | 201 Created   | Tạo một tài nguyên mới            |
| PUT         | `/resources/{id}`    | 200 OK        | Cập nhật toàn bộ tài nguyên       |
| PATCH       | `/resources/{id}`    | 200 OK        | Cập nhật một phần tài nguyên      |
| DELETE      | `/resources/{id}`    | 204 No Content| Xóa một tài nguyên                |

### 3.3 Thiết Kế Dữ Liệu của API (Designing the API’s Data)

Dữ liệu là trung tâm của API REST. Thiết kế dữ liệu bao gồm việc xác định các khái niệm, phản hồi và tham số.

#### 3.3.1 Thiết Kế Khái Niệm (Designing Concepts)

Khái niệm là các thực thể chính trong API, chẳng hạn như "người dùng" hoặc "bài đăng". Mỗi khái niệm được biểu diễn dưới dạng một đối tượng JSON với các thuộc tính.

Ví dụ, khái niệm "người dùng" có thể bao gồm:

- **id**: Chuỗi, định danh duy nhất.
- **name**: Chuỗi, tên người dùng.
- **email**: Chuỗi, địa chỉ email.
- **birthdate**: Chuỗi, ngày sinh (định dạng ISO 8601, ví dụ: `1990-01-01`).

Đối tượng JSON:

```json
{
  "id": "123",
  "name": "John Doe",
  "email": "john.doe@example.com",
  "birthdate": "1990-01-01"
}
```

Khi thiết kế khái niệm, hãy đảm bảo:

- **Tên rõ ràng**: Sử dụng tên dễ hiểu (ví dụ: `name` thay vì `userName`).
- **Định dạng chuẩn**: Sử dụng các chuẩn như ISO 8601 cho ngày tháng.
- **Kiểu dữ liệu phù hợp**: Chọn kiểu dữ liệu phù hợp (chuỗi, số, boolean, v.v.).

#### 3.3.2 Thiết Kế Phản Hồi từ Khái Niệm (Designing Responses from Concepts)

Phản hồi của API thường là biểu diễn của một khái niệm hoặc danh sách các khái niệm. Dựa trên khái niệm "người dùng", phản hồi cho yêu cầu `GET /users/123` có thể là:

```json
{
  "id": "123",
  "name": "John Doe",
  "email": "john.doe@example.com",
  "birthdate": "1990-01-01"
}
```

Đối với yêu cầu `GET /users`, phản hồi có thể là một mảng:

```json
[
  {
    "id": "123",
    "name": "John Doe",
    "email": "john.doe@example.com",
    "birthdate": "1990-01-01"
  },
  {
    "id": "124",
    "name": "Jane Smith",
    "email": "jane.smith@example.com",
    "birthdate": "1995-05-10"
  }
]
```

Khi thiết kế phản hồi, hãy xem xét:

- **Cấu trúc nhất quán**: Tất cả phản hồi nên có cấu trúc tương tự.
- **Dữ liệu cần thiết**: Chỉ bao gồm các trường cần thiết để tránh dư thừa.

#### 3.3.3 Thiết Kế Tham Số từ Khái Niệm hoặc Phản Hồi (Designing Parameters from Concepts or Responses)

Tham số là dữ liệu được gửi trong yêu cầu, chẳng hạn như tham số đường dẫn, tham số truy vấn, hoặc phần thân yêu cầu. Các tham số thường được suy ra từ khái niệm hoặc phản hồi.

Ví dụ, để tạo một người dùng mới (`POST /users`), phần thân yêu cầu có thể bao gồm:

```json
{
  "name": "Jane Smith",
  "email": "jane.smith@example.com",
  "birthdate": "1995-05-10"
}
```

Tham số truy vấn có thể được sử dụng để lọc dữ liệu, chẳng hạn như:

```
GET /users?email=jane.smith@example.com
```

Khi thiết kế tham số, hãy đảm bảo:

- **Tính cần thiết**: Chỉ yêu cầu các tham số bắt buộc.
- **Định dạng rõ ràng**: Xác định định dạng dữ liệu (ví dụ: email phải hợp lệ).
- **Nguồn dữ liệu**: Kiểm tra xem tham số có thể được lấy từ đâu (ví dụ: từ cơ sở dữ liệu hoặc đầu vào người dùng).

#### 3.3.4 Kiểm Tra Nguồn Dữ Liệu Tham Số (Checking Parameter Data Sources)

Hãy đảm bảo rằng các tham số có nguồn dữ liệu rõ ràng. Ví dụ:

- **ID người dùng**: Được cung cấp bởi ứng dụng khách hoặc được tạo bởi máy chủ.
- **Email**: Được người dùng nhập vào.
- **Ngày sinh**: Có thể được lấy từ hồ sơ người dùng hoặc yêu cầu nhập.

Nếu một tham số không có nguồn dữ liệu rõ ràng, điều đó có thể chỉ ra một vấn đề trong thiết kế mục tiêu API.

#### 3.3.5 Thiết Kế Các Tham Số Khác (Designing Other Parameters)

Ngoài các tham số dựa trên khái niệm, API có thể yêu cầu các tham số bổ sung, chẳng hạn như:

- **Tham số phân trang**: `page` và `pageSize` để kiểm soát số lượng bản ghi trả về.
- **Tham số sắp xếp**: `sort` để sắp xếp kết quả (ví dụ: `sort=name,asc`).
- **Tham số lọc**: `filter` để giới hạn kết quả (ví dụ: `filter=email:jane.smith@example.com`).

Ví dụ:

```
GET /users?page=2&pageSize=10&sort=name,asc
```

### 3.4 Tìm Kiếm Sự Cân Bằng Khi Đối Mặt với Các Thách Thức Thiết Kế (Striking a Balance When Facing Design Challenges)

Thiết kế API REST thường đòi hỏi sự cân bằng giữa tính thân thiện với người dùng và tuân thủ các nguyên tắc REST.

#### 3.4.1 Ví Dụ Về Sự Đánh Đổi Trong REST (REST Trade-off Examples)

Hãy xem xét một số tình huống mà bạn phải đưa ra quyết định thiết kế:

- **Tài nguyên Hành động (Action Resources)**: Giả sử bạn cần một hành động để gửi lời mời kết bạn. Theo REST, bạn nên sử dụng tài nguyên, chẳng hạn như:

```
POST /friend-invitations
{
  "fromUserId": "123",
  "toUserId": "124"
}
```

Tuy nhiên, nếu hành động này không phù hợp với mô hình tài nguyên, bạn có thể cân nhắc sử dụng một API không hoàn toàn REST, chẳng hạn như:

```
POST /users/123/invite-friend
{
  "toUserId": "124"
}
```

- **Phân trang và Lọc**: Để cải thiện hiệu suất, bạn có thể thêm tham số phân trang và lọc, nhưng điều này có thể làm phức tạp API. Ví dụ:

```
GET /users?page=1&pageSize=10&filter=email:jane.smith@example.com
```

Bạn cần cân nhắc giữa sự đơn giản và tính linh hoạt.

#### 3.4.2 Cân Bằng Tính Thân Thiện Với Người Dùng và Tuân Thủ (Balancing User-friendliness and Compliance)

REST khuyến khích sử dụng các phương thức HTTP tiêu chuẩn và cấu trúc tài nguyên, nhưng đôi khi bạn cần ưu tiên trải nghiệm người dùng. Ví dụ, nếu ứng dụng khách cần một API đơn giản hơn, bạn có thể cung cấp một điểm cuối tổng hợp:

```
GET /user-profile/123
```

Thay vì yêu cầu ứng dụng khách thực hiện nhiều lời gọi:

```
GET /users/123
GET /users/123/posts
GET /users/123/friends
```

Tuy nhiên, bạn nên đảm bảo rằng các quyết định này được ghi chép rõ ràng và không làm mất đi tính nhất quán của API.

### 3.5 Hiểu Tại Sao REST Quan Trọng Đối Với Thiết Kế của Bất Kỳ API Nào (Understanding Why REST Matters for the Design of Any API)

Mặc dù chương này tập trung vào API REST, các nguyên tắc của REST có thể áp dụng cho bất kỳ loại API nào.

#### 3.5.1 Giới Thiệu Phong Cách Kiến Trúc REST (Introducing the REST Architectural Style)

REST là một phong cách kiến trúc, không phải một tiêu chuẩn nghiêm ngặt. Nó bao gồm sáu ràng buộc:

1. **Tách biệt ứng dụng khách/máy chủ (Client/Server Separation)**: Tách biệt trách nhiệm giữa ứng dụng khách và máy chủ, cải thiện khả năng mở rộng.
2. **Không trạng thái (Stateless)**: Mỗi yêu cầu phải độc lập, giảm tải cho máy chủ.
3. **Khả năng lưu trữ (Cacheability)**: Phản hồi có thể được lưu trữ để cải thiện hiệu suất.
4. **Giao diện thống nhất (Uniform Interface)**: Sử dụng các phương thức, đường dẫn và mã trạng thái tiêu chuẩn.
5. **Hệ thống phân tầng (Layered System)**: Cho phép thêm các lớp như proxy hoặc cổng API.
6. **Mã theo yêu cầu (Code on Demand)**: Máy chủ có thể cung cấp mã thực thi cho ứng dụng khách (hiếm khi sử dụng).

Những ràng buộc này làm cho API REST dễ mở rộng, đáng tin cậy và có thể tái sử dụng.

#### 3.5.2 Ảnh Hưởng của Các Ràng Buộc REST Đối Với Thiết Kế API (The Impact of REST Constraints on API Design)

Các ràng buộc REST ảnh hưởng đến thiết kế API theo những cách sau:

- **Tách biệt ứng dụng khách/máy chủ**: Khuyến khích thiết kế API độc lập với giao diện người dùng, cho phép sử dụng lại API cho nhiều ứng dụng khách.
- **Không trạng thái**: Đảm bảo rằng API có thể xử lý nhiều yêu cầu đồng thời mà không cần lưu trữ trạng thái, cải thiện khả năng mở rộng.
- **Khả năng lưu trữ**: Cho phép ứng dụng khách lưu trữ phản hồi, giảm số lượng yêu cầu đến máy chủ.
- **Giao diện thống nhất**: Đảm bảo rằng API dễ hiểu và nhất quán, giảm thời gian học hỏi cho các nhà phát triển.

Những nguyên tắc này có thể được áp dụng cho các API không phải REST, chẳng hạn như GraphQL hoặc gRPC, để cải thiện thiết kế tổng thể.

### Ví Dụ Minh Họa (Example)

Để minh họa các khái niệm trong Chương 3, hãy xem xét việc thiết kế một API REST cho một ứng dụng quản lý thư viện. Mục tiêu là cho phép người dùng:

1. Lấy danh sách tất cả sách.
2. Lấy thông tin chi tiết về một cuốn sách.
3. Thêm một cuốn sách mới.
4. Cập nhật thông tin cuốn sách.
5. Xóa một cuốn sách.

#### Bước 1: Xác Định Mục Tiêu API (Sử dụng Canvas Mục Tiêu API)

| Cái gì?                     | Ai?                | Như thế nào?                          | Nguồn đầu vào?           | Đầu ra?                       |
|-----------------------------|--------------------|---------------------------------------|--------------------------|-------------------------------|
| Lấy danh sách sách          | Ứng dụng web       | Truy xuất tất cả sách                 | Không có                 | Danh sách sách (ID, tiêu đề, tác giả) |
| Lấy chi tiết sách           | Ứng dụng web       | Truy xuất sách dựa trên ID            | ID sách                  | ID, tiêu đề, tác giả, năm xuất bản |
| Thêm sách mới               | Quản trị viên      | Tạo sách mới                          | Tiêu đề, tác giả, năm    | Thông tin sách đã tạo        |
| Cập nhật sách               | Quản trị viên      | Cập nhật thông tin sách dựa trên ID   | ID sách, tiêu đề, tác giả, năm | Thông tin sách đã cập nhật |
| Xóa sách                    | Quản trị viên      | Xóa sách dựa trên ID                  | ID sách                  | Không có                     |

#### Bước 2: Xác Định Tài Nguyên và Hành Động

- **Tài nguyên**: Sách (`books`).
- **Hành động**:
  - Lấy danh sách: GET `/books`.
  - Lấy chi tiết: GET `/books/{id}`.
  - Thêm mới: POST `/books`.
  - Cập nhật: PUT `/books/{id}`.
  - Xóa: DELETE `/books/{id}`.

#### Bước 3: Thiết Kế Dữ Liệu

Khái niệm "sách":

```json
{
  "id": "string",
  "title": "string",
  "author": "string",
  "year": "number"
}
```

#### Bước 4: Ánh Xạ Thành API REST

1. **Lấy danh sách sách**:

```
GET /books
```

Phản hồi:

```json
[
  {
    "id": "1",
    "title": "The Great Gatsby",
    "author": "F. Scott Fitzgerald",
    "year": 1925
  },
  {
    "id": "2",
    "title": "1984",
    "author": "George Orwell",
    "year": 1949
  }
]
```

2. **Lấy chi tiết sách**:

```
GET /books/1
```

Phản hồi:

```json
{
  "id": "1",
  "title": "The Great Gatsby",
  "author": "F. Scott Fitzgerald",
  "year": 1925
}
```

3. **Thêm sách mới**:

```
POST /books
Content-Type: application/json

{
  "title": "To Kill a Mockingbird",
  "author": "Harper Lee",
  "year": 1960
}
```

Phản hồi:

```json
{
  "id": "3",
  "title": "To Kill a Mockingbird",
  "author": "Harper Lee",
  "year": 1960
}
```

4. **Cập nhật sách**:

```
PUT /books/3
Content-Type: application/json

{
  "title": "To Kill a Mockingbird",
  "author": "Harper Lee",
  "year": 1961
}
```

Phản hồi:

```json
{
  "id": "3",
  "title": "To Kill a Mockingbird",
  "author": "Harper Lee",
  "year": 1961
}
```

5. **Xóa sách**:

```
DELETE /books/3
```

Phản hồi: Mã trạng thái 204 No Content.

#### Bước 5: Cân Nhắc Thách Thức Thiết Kế

Giả sử ứng dụng web cần lấy danh sách sách cùng với thông tin chi tiết về tác giả. Thay vì yêu cầu ứng dụng khách thực hiện nhiều lời gọi (`GET /books` và `GET /books/{id}/author`), bạn có thể cung cấp một điểm cuối tổng hợp:

```
GET /books?include=author
```

Phản hồi:

```json
[
  {
    "id": "1",
    "title": "The Great Gatsby",
    "author": {
      "name": "F. Scott Fitzgerald",
      "birthYear": 1896
    },
    "year": 1925
  },
  {
    "id": "2",
    "title": "1984",
    "author": {
      "name": "George Orwell",
      "birthYear": 1903
    },
    "year": 1949
  }
]
```

Quyết định này làm tăng tính thân thiện với người dùng nhưng có thể làm phức tạp thiết kế API. Bạn cần ghi chép rõ ràng cách sử dụng tham số `include`.

#### Bước 6: Áp Dụng Nguyên Tắc REST

- **Không trạng thái**: Mỗi yêu cầu như `GET /books/1` chứa đầy đủ thông tin (ID sách) để máy chủ xử lý.
- **Khả năng lưu trữ**: Thêm tiêu đề `Cache-Control` vào phản hồi để cho phép lưu trữ:

```
GET /books/1
Cache-Control: max-age=3600
```

- **Giao diện thống nhất**: Sử dụng danh từ (`books`), phương thức HTTP chuẩn, và mã trạng thái phù hợp.
